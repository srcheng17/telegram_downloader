# 上传 CBZ、首页历史与日志动作改造设计（2026-03-18）

## 背景

当前项目已经具备：

- 首页 URL 提交与元数据填写
- 日志页轮询、取消、下载预检与下载
- 设置页核心下载参数持久化
- CBZ 生成与 `ComicInfo.xml` 元数据写入

但当前流程仍存在几个明显缺口：

1. 首页只能发起 URL 下载，不能直接上传压缩包转成 CBZ。
2. 首页仍保留“下载护栏说明”，而用户更需要最近填写过的元数据历史。
3. 元数据清洗规则不完整，尤其是作者分隔符与提示文案不一致。
4. 日志页“下载”动作只有浏览器下载一种模式，不能切换为复制到 Komga 目录。
5. 现有任务模型无法清晰地区分“URL 任务”和“上传任务”，也不支持上传中进度、上传失败一键重试、上传中取消。

本次设计的目标是在不拆成两套系统的前提下，把 **URL 下载** 与 **压缩包上传转 CBZ** 统一到一套任务模型、日志模型和最终产物动作中。

## 已确认约束

- 首页任务入口采用 **单选切换**：`URL 下载` / `上传压缩包`。
- 上传格式支持 **ZIP / RAR / 7Z**。
- 日志页中的上传任务必须和 URL 任务一样，作为 **正式任务** 出现在同一张日志表中。
- 日志表中必须有明显标识区分 **上传任务** 与 **URL 任务**。
- 上传失败后点击“重试”时，**复用同一条日志记录**，不新建任务。
- 上传失败允许一键重试，因此服务端需要暂存原始上传包。
- 原始上传包的清理策略与现有文件保留期统一：**成功/取消立即删，失败保留并按文件保留期清理**。
- 首页最近 20 条历史在 **成功进入队列 / 成功创建上传任务后** 记录；前端校验失败的不记录。
- 点击首页历史项后：
  - 恢复元数据字段
  - 自动切换到对应任务类型
  - 如果历史项来自 URL 任务，则恢复 URL
  - 如果历史项来自上传任务，则不恢复本地文件，只恢复元数据
- 设置页只新增简单的 **二选一下载动作模式**：
  - `browser`：浏览器下载（默认）
  - `komga_copy`：复制到 Komga
- Komga 根目录固定为：
  - `/Users/ryancheng/docker_data/komga/data/myReadingManga`
- 若有系列名，复制到系列目录；若无系列名，复制到 `tanbokon/`。
- 该 Komga 路径已在 **2026-03-18** 的当前开发环境中确认存在，但运行时仍要逐次校验目录可写与文件复制结果。
- 新的 CBZ 文件名规则为：
  - `作者_系列名_漫画名_时间戳.cbz`
  - 无系列名时省略系列名段

## 目标

### 业务目标

1. 用户可以不依赖 URL，直接上传 ZIP / RAR / 7Z 并生成 CBZ。
2. 首页能快速复用最近 20 条元数据历史，提高重复录入效率。
3. 日志页能够稳定展示上传任务的进度、取消、失败重试与最终产物动作。
4. 用户可在设置中切换“浏览器下载”与“复制到 Komga”两种后续动作。

### 技术目标

1. 任务系统继续维持单一主线，而不是新增一套“上传专用日志系统”。
2. URL 任务与上传任务共用状态机、日志表和产物访问边界。
3. 元数据清洗规则统一落在共享逻辑中，不再由模板提示和后端行为各说各话。
4. 产物命名、复制路径、失败重试和清理策略都由后端单点决定。

### 非目标

- 不在本轮加入可编辑 Komga 根路径。
- 不在本轮加入“浏览器下载 + Komga 复制同时执行”模式。
- 不把上传任务做成前端临时态或独立上传面板。
- 不扩展为通用文件管理器或通用漫画库同步系统。

## 可选方案与采用方案

### 方案 1：统一任务模型，上传/URL 共用一套日志与产物流程（采用）

做法：

- 扩展任务模型，加入任务类型、上传源包信息、上传进度字段与重试能力
- 上传时先创建正式任务，再写入文件并更新上传进度
- 日志页统一展示 URL / 上传两类任务
- 下载按钮统一走“产物动作”接口，由设置决定是浏览器下载还是复制到 Komga

优点：

- 与现有日志页和任务系统最一致
- 刷新页面不会丢上传状态
- “同一条日志里取消 / 重试 / 成功下载”语义自然

缺点：

- 后端表结构、HTTP 接口、前端页面与测试都要同步改造

### 方案 2：上传单独做上传会话，完成后再生成正式任务

优点：

- 上传与处理边界清晰

缺点：

- 需要两套状态映射
- 难以满足“上传中就在日志页正式可见”与“失败重试复用同一条记录”

### 方案 3：前端维护临时上传态，上传完成后才创建正式任务

优点：

- 初期改动最少

缺点：

- 上传状态刷新即丢失
- 日志中的上传任务不是真实任务，重试/取消难以可靠实现

### 采用理由

采用方案 1。它是唯一能同时满足以下要求的方案：

- 上传任务在日志页中是真正的任务
- 上传进度可轮询可恢复
- 失败后能一键重试且复用同一条记录
- URL 任务与上传任务共享统一后端边界

## 总体架构

本次改造围绕三个核心对象展开：

1. **任务记录**
   - URL 任务与上传任务都落在统一任务表 / 统一任务响应模型中
2. **元数据历史**
   - 记录最近 20 条已成功进入任务系统的首页输入
3. **产物动作**
   - 成功任务的“下载”按钮不再只代表浏览器下载，而是代表“执行当前设置对应的产物动作”

### 架构原则

1. 首页只有一个表单，但入口模式互斥。
2. 上传流程不是前端私有流程，而是正式任务生命周期的一部分。
3. 前端只显示后端状态，不自己推断“是否可重试/是否可复制”这类核心规则。
4. 成功产物的最终文件位置仍以任务产物路径为真，相对 Komga 复制属于派生动作。

## 首页设计

## 首页入口切换

首页在当前表单区顶部新增单选控件：

- `URL 下载`
- `上传压缩包`

行为规则：

- 选 `URL 下载`：
  - URL 输入框启用
  - 文件选择控件禁用或隐藏
- 选 `上传压缩包`：
  - 文件选择控件启用
  - URL 输入框禁用或隐藏

页面约束为“二选一”，任何一次提交只能携带一种来源。

## 元数据字段

两种入口共用一套元数据字段：

- 作者
- 漫画系列名
- 漫画名
- 书籍详情介绍
- 标签
- 类型

这些字段继续写入任务记录，并用于生成 `ComicInfo.xml` 和最终文件名。

## 首页最近 20 条元数据历史

首页原“下载护栏说明”区域替换为“最近 20 条元数据历史”。

每条历史项至少展示：

- 任务类型（URL / 上传）
- 作者
- 系列名
- 漫画名
- 最近填写时间
- URL（仅 URL 历史项展示摘要）

点击历史项时：

- 恢复作者 / 系列名 / 漫画名 / 简介 / 标签 / 类型
- 自动切换到历史项对应的任务类型
- 若为 URL 历史项，则恢复 URL 字段
- 若为上传历史项，则不恢复文件，只切换到上传模式

## 字段提示折叠

“作者 / 标签 / 类型”的分隔符提示不再始终展开，而是放入可点击展开的说明区域。默认折叠，点击标题旁的说明按钮或提示标题才展开。

这样既保留行为说明，又减少首页首屏噪音。

## 元数据归一化

### 作者

作者字段支持以下分隔符：

- 英文逗号 `,`
- 中文逗号 `，`
- 半角井号 `#`
- 全角井号 `＃`

归一化规则：

- 分隔后逐项 `trim`
- 空项丢弃
- 去重，保留首次出现顺序
- 最终用英文逗号拼接

### 标签 / 类型

标签与类型字段支持以下分隔符：

- 英文逗号 `,`
- 中文逗号 `，`
- 空白字符（空格、多个空格、换行）
- 半角井号 `#`
- 全角井号 `＃`

归一化规则与作者一致，最终也统一为英文逗号拼接。

## 日志页设计

## 日志列表列变化

日志表新增或调整以下展示语义：

- **任务类型列**
  - `URL`
  - `上传`
- **进度列**
  - URL 任务：继续显示图片进度，如 `12 / 30`
  - 上传任务上传中：显示字节进度，如 `12 MB / 80 MB`
  - 上传任务处理中：显示“处理中”
  - 成功：显示完成
- **操作列**
  - 活动态：取消
  - 失败上传任务：重试
  - 成功任务：下载（实际行为受设置控制）

## 上传任务日志行为

上传任务必须作为正式任务与 URL 任务一起出现在日志页中，并具备明确状态标识。

建议任务类型标识直接作为一列展示，而不是只体现在状态文案里。这样筛选、人工检查和后续扩展都更清晰。

## 上传任务状态机

统一采用扩展后的正式状态流转：

- `UPLOADING`
- `QUEUED`
- `RUNNING`
- `CANCEL_REQUESTED`
- `SUCCESS`
- `FAILED`
- `CANCELED`

说明：

- `UPLOADING` 表示浏览器正在向服务端传输原始压缩包
- `QUEUED` / `RUNNING` 表示上传已完成、后端正在解包/校验/重打包
- `CANCEL_REQUESTED` / `CANCELED` 与现有任务取消语义保持一致

URL 任务继续使用现有状态集，不需要伪造 `UPLOADING`。

## 上传失败重试

失败上传任务点击“重试”后：

- 不创建新任务
- 复用同一条任务记录
- 状态从 `FAILED` 重新进入上传后处理阶段
- 直接使用服务端保留的原始上传包重跑

如果原始上传包已被清理或损坏：

- 后端返回明确错误
- 前端提示“源文件已清理，无法重试”

## 取消规则

### 上传中取消

- 中断当前上传流
- 清理未完成临时文件
- 任务转为 `CANCELED` 或先到 `CANCEL_REQUESTED` 再进入 `CANCELED`

### 处理中取消

- 与现有 worker 取消语义一致
- 允许先进入 `CANCEL_REQUESTED`
- 处理线程检测到取消后转 `CANCELED`

### 终态

成功 / 失败 / 已取消任务不可再次取消。

## 后端数据设计

## 任务模型扩展

现有任务记录需要扩展以下字段（命名可按当前仓内风格微调）：

- `task_type`
  - `url`
  - `upload`
- `source_archive_path`
  - 原始上传包服务端存放路径
- `source_archive_name`
  - 用户上传时的原始文件名
- `upload_loaded_bytes`
- `upload_total_bytes`
- `retryable`
  - 对上传任务表示是否允许一键重试

如果当前 V2 任务模型已成为主线，则这些字段优先落在 `v2_tasks`；legacy-facing adapter 继续将其映射到前端所需响应。

## 元数据历史存储

新增一份独立历史存储，记录最近 20 条首页输入：

- `id`
- `task_type`
- `url`（URL 任务才有）
- `author`
- `series_name`
- `comic_name`
- `summary`
- `tags`
- `genres`
- `created_at`

存储规则：

- 成功进入任务系统后写入
- 读取时按时间倒序取最近 20 条
- 同一份元数据可重复出现，不强制去重；去重策略不是本轮必要需求

## 设置存储扩展

在现有设置快照中新增：

- `download_action_mode`
  - `browser`
  - `komga_copy`

默认值为 `browser`。

本轮不新增根路径配置，因此设置页只暴露模式切换，不暴露路径编辑。

## 上传处理流程

### 阶段 1：创建上传任务

首页选择上传并提交后，后端先创建正式任务：

- `task_type = upload`
- `status = UPLOADING`
- 持久化元数据

这样日志页立刻能看见该任务。

### 阶段 2：接收原始压缩包

服务端将上传文件写入临时目录，例如：

- `temp_uploads/<task-id>/source.<ext>`

写入过程中持续更新：

- `upload_loaded_bytes`
- `upload_total_bytes`
- `status = UPLOADING`

### 阶段 3：上传完成后进入后处理

文件写入成功后：

- 校验扩展名与基础可读性
- 根据类型走 ZIP / RAR / 7Z 解包路径
- 筛出图片文件
- 生成 `ComicInfo.xml`
- 按规则重新打包为 `.cbz`

随后任务进入：

- `QUEUED` 或直接 `RUNNING`

具体由当前执行架构决定：

- 若继续沿用 queue/worker，则上传完成后 enqueue
- 若上传处理在 API 进程中直接转 worker 风格用例，则必须保持状态语义一致

### 阶段 4：任务收尾

#### 成功

- 写入 `result_zip_path`
- `retryable = false`
- 删除 `source_archive_path`

#### 失败

- 保留 `source_archive_path`
- `retryable = true`
- 错误信息写入任务

#### 取消

- 清理中间目录与未完成产物
- 删除 `source_archive_path`
- 任务转 `CANCELED`

## ZIP / RAR / 7Z 支持

实现上允许采用不同解包后端，但对任务系统表现必须统一：

- 都输入“原始压缩包路径”
- 都输出“图片文件集合”
- 都复用同一套图片筛选、排序、CBZ 重打包流程

无论底层使用 Go 库还是系统命令，业务层接口都应抽象成统一的 archive extractor，避免将格式差异散落在 handler 或 worker 中。

## 产物命名

最终产物名统一为：

- 有系列名：`作者_系列名_漫画名_时间戳.cbz`
- 无系列名：`作者_漫画名_时间戳.cbz`

兜底规则：

- 作者为空时使用 `未知作者`
- 漫画名为空时使用 `未命名漫画`
- 系列名为空时该段完全省略，不保留多余下划线

命名清洗继续沿用现有非法文件名字符过滤与长度截断逻辑。

## Komga 复制模式

## 固定根目录

Komga 根目录固定为：

- `/Users/ryancheng/docker_data/komga/data/myReadingManga`

运行时每次执行复制动作仍需校验：

- 根目录存在
- 目标目录可创建
- 文件可写

## 目标路径规则

- 有系列名：
  - `myReadingManga/<系列名>/<文件名>.cbz`
- 无系列名：
  - `myReadingManga/tanbokon/<文件名>.cbz`

若目标目录不存在，则自动创建。

## 日志页按钮语义

成功任务在日志页仍显示“下载”按钮，但其实际动作由设置决定：

- `browser`
  - 保持现有下载/预检流程
- `komga_copy`
  - 调用复制动作接口
  - 成功后在日志页内联提示目标路径
  - 失败时展示明确错误，不离开日志页

本轮建议同名文件采用 **覆盖写入**。这是最符合“同一任务重复执行即更新结果”的策略，也能避免额外的重命名规则与路径冲突 UI。

## HTTP 与前端契约变化

## 首页提交

首页提交接口需要支持两类请求：

1. URL 提交
2. 上传提交

上传提交建议走专门上传入口，而不是强行复用 `application/x-www-form-urlencoded` 的 `/download`：

- `POST /api/tasks/upload`
  - `multipart/form-data`
  - 包含：
    - `archive`
    - `author`
    - `series_name`
    - `comic_name`
    - `summary`
    - `tags`
    - `genres`

URL 提交可继续保留现有 `/download`，由首页根据模式选择对应入口。这样可以最小化对现有 URL 提交流程的破坏。

## 元数据历史接口

新增读取接口，例如：

- `GET /api/metadata-history?limit=20`

仅返回前端回填所需字段。

## 上传重试接口

新增上传任务重试接口，例如：

- `POST /api/tasks/{task_id}/retry`

仅对：

- `task_type = upload`
- `status = FAILED`
- `retryable = true`

的任务生效。

## 产物动作接口

成功任务当前的下载接口可以分两种策略：

### 策略 A：保留下载接口，新增复制接口（推荐）

- 浏览器下载继续使用现有：
  - `HEAD /api/tasks/{task_id}/download`
  - `GET /api/tasks/{task_id}/download`
- Komga 复制新增：
  - `POST /api/tasks/{task_id}/copy-to-komga`

前端根据设置调用不同接口。这样最清晰，也最不容易破坏现有下载预检。

### 策略 B：统一成单一动作接口

前端总是调一个“执行产物动作”的接口，再由服务端根据设置决定是下载还是复制。

本轮采用 **策略 A**。因为：

- 现有浏览器下载链路已稳定
- 复制动作不是下载，不适合强塞进同一路由
- 前端根据设置显式分流，更容易测试和调试

## 测试设计

## 前端单测

至少覆盖：

- 首页模式切换的互斥行为
- 作者 / 标签 / 类型分隔符归一化
- 元数据历史点击回填与模式切换
- 折叠提示展开/收起
- 日志页任务类型与操作按钮渲染

## 前端 E2E

至少覆盖：

- URL 任务提交流程仍可用
- 上传任务创建后立即出现在日志中
- 上传进度在日志页刷新可见
- 上传中取消
- 上传失败后重试复用同一条日志
- 设置为 `komga_copy` 后，日志成功任务按钮走复制分支而不是浏览器下载

## 后端单测

至少覆盖：

- 上传任务创建与状态流转
- ZIP / RAR / 7Z 的统一解包入口
- 文件名规则
- Komga 目标路径选择
- 上传失败的 `retryable` 与源包保留
- 成功 / 取消时立即清理源包

## 集成测试

至少覆盖：

- 上传 -> 生成 CBZ -> 成功产物可访问
- 上传失败 -> 重试 -> 成功 -> 清理源包
- 设置切为 `komga_copy` 后复制成功写入正确目录层级

## 风险与边界

### RAR / 7Z 的实现依赖

RAR / 7Z 可能需要额外 Go 库或系统依赖。设计要求是：

- 差异只存在于 archive extractor 实现层
- 不能污染 handler、前端或任务状态机

### 上传进度持久化频率

上传进度更新不能过于频繁地写库。实现时应采用节流更新，但前端看到的体验仍需足够平滑。

### 取消与重试的一致性

上传任务的取消和重试必须保证：

- 不残留部分写入的源包或半成品 CBZ
- 不出现“同一任务同时被多个重试执行”这种竞态

## 实现切片建议

实现应按以下顺序推进：

1. 扩展任务表 / 设置表 / 元数据历史存储
2. 打通最小上传闭环（先 ZIP）
3. 将日志页与首页接到正式上传任务模型
4. 补齐失败重试、取消与清理
5. 扩展 RAR / 7Z
6. 补齐 Komga 复制模式与设置页切换
7. 完成前端 E2E 与后端集成验证

先打通 ZIP 最小闭环不是缩减需求，而是为了降低并行复杂度；最终交付仍必须包含 ZIP / RAR / 7Z 三种格式。

## 规划准备结论

该需求可以作为一个单一实现计划推进，不需要拆成多个完全独立的项目。核心原因是：

- 上传任务、URL 任务、首页历史、日志动作切换都围绕同一任务域模型变化
- 它们共享前端页面、共享任务状态和共享后端产物语义

因此后续 implementation plan 应围绕一个统一特性拆任务，而不是拆成相互独立的多个计划。
