# 运行时 Go 化与稳定性/可维护性优化设计（方案 A）

## 1. 目标与边界

### 1.1 核心目标
- 运行时完全 Go 化：以 `go-api + go-worker + postgres + redis + gateway` 作为唯一生产链路。
- 优先提升稳定性与资源效率：降低失败率、重试风暴和僵尸任务概率，控制内存/CPU 抖动。
- 同步提升可维护性：明确模块职责边界，减少重复编排逻辑，提升可测试性。

### 1.2 明确边界
- 本轮不做功能扩张，聚焦“治理与替代”。
- Python 代码保留为历史归档与迁移参考，不再参与默认运行链路。
- 对外行为尽量兼容，激进变更仅限内部架构与执行路径。

### 1.3 验收导向
- 稳定性：失败分类清晰、可重试错误比例下降、任务状态最终一致。
- 资源效率：内存峰值下降、CPU 抖动降低、队列积压更可控。
- 可维护性：编排逻辑收敛、核心模块可独立测试、文档与运行路径一致。

---

## 2. 目标架构与模块拆分

### 2.1 目标运行架构（保持单主线）

```text
gateway -> go-api -> postgres/redis
            |
            +-> go-worker (redis streams consumer)
```

- `go-api`：负责页面与 API 协议层、任务入队、状态查询与下载服务。
- `go-worker`：负责任务执行、下载打包、状态推进与失败重试。
- Python 不在 runtime 拓扑内。

### 2.2 Go 分层目标
- **transport 层**：`httpui/httpapi/httpv2` 仅做协议转换、输入校验、响应组装。
- **application/service 层**：任务编排、状态机推进、重试决策、幂等与超时策略。
- **domain 层**：任务模型、错误模型、状态流转规则。
- **infrastructure 层**：postgres repo、redis stream、downloader、cbz writer。

目标是把散落在 handler/worker 的策略判断收敛到 application/domain，降低跨层耦合。

### 2.3 下载执行链路优化方向
- 优先采用“流式落盘 + 打包”，避免大任务全量内存持有。
- 建立“全局预算 + 单任务预算”的并发治理，避免 worker 间资源争抢。
- 细化重试策略：仅可重试错误进入退避重试，减少无效放大。

### 2.4 状态机与恢复能力
- 统一任务状态更新入口，避免多处分支导致状态不一致。
- 强化 pending reclaim / cancel / timeout 的协同处理。
- 保证任务“可终止、可恢复、可追踪”。

## 3. 分阶段实施与回滚策略

### Phase 0：基线与护栏
- 增加结构化日志与关键指标：下载耗时、失败分类、重试次数、任务卡住时长、资源快照。
- 建立优化基线与回归阈值，避免“主观优化”。

### Phase 1：稳定性与资源效率治理（最高优先）
- 下载链路流式化与限额治理（任务级/worker级并发预算）。
- 重试与退避策略收敛，建立错误分级（可重试/不可重试）。
- 收敛取消与恢复流程，降低僵尸任务与重复执行。

### Phase 2：可维护性重构
- 提炼 application service 层，清理 handler/worker 中重复编排逻辑。
- 统一错误模型与状态推进 API，减少隐式分支。
- 补齐模块级与契约级测试。

### Phase 3：Python 运行时退场
- 文档、脚本、CI 默认路径切为 Go 主线。
- Python 标记为 `legacy/archive`，不参与默认执行流程。
- 验证 compose、网关、健康检查、E2E 全链路仅依赖 Go。

### 分阶段回滚原则
- 每个 Phase 独立提交、可独立回退。
- 行为变化前保留兼容层或特性开关，支持灰度。
- 每阶段完成后必须通过测试与 smoke 才进入下一阶段。

---

## 4. 测试与验收标准

### 4.1 测试金字塔
- 单元：`downloader / retry policy / state transition / repo`。
- 集成：`go-api + postgres + redis` 核心任务生命周期。
- E2E：提交任务、日志查看、下载产物、设置项生效。

### 4.2 稳定性验收
- 失败可归类（网络、源站、资源限制、内部错误）。
- 可重试错误在退避策略下成功率提升且无重试风暴。
- 取消/超时/中断后任务最终状态一致，无长时间卡死。

### 4.3 资源效率验收
- 大图与多图场景内存峰值较基线下降。
- 并发场景 CPU 更平稳，队列 lag 可控。
- 并发配置变化不会引发雪崩式失败。

### 4.4 可维护性验收
- 编排逻辑集中到 service/domain，handler/worker 职责清晰。
- 关键模块具备独立测试，故障定位路径明确。
- 主链路、排障、迁移、回滚文档保持一致。

---

## 5. 设计结论

采用**方案 A（稳态优先分层治理）**：
先建立指标与护栏，再进行稳定性/资源效率治理，随后推进可维护性重构，最后完成 Python 运行时退场与文档收敛。

该路径最符合“分阶段改造 + 稳定性优先 + 可维护性优先”的目标组合。
