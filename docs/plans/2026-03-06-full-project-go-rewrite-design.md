# 全项目重构优化设计（Go 全面重写，单阶段切换）

## 1. 背景与目标

当前项目处于 Python/Go 混合过渡状态，接口、部署与运维路径复杂，维护成本高。
本次重构目标是：在 5-8 周内完成一次性全量重写与替换，形成单一 Go 主线系统，并完成历史数据全量迁移。

### 已确认约束

- 目标形态：全面 Go 化（Go API + Go Worker 唯一主线）。
- 协议策略：允许重定 API 与前端整体改造。
- 优先级：可维护性、性能、交付速度全部高优先级。
- 迁移方式：激进单阶段重写与切换（不做长期双栈）。
- 数据策略：历史任务数据全量迁移。
- 部署形态：Docker Compose。

---

## 2. 目标架构与系统边界

### 2.1 运行组件

- `go-api`：统一对外 API、静态资源与管理接口。
- `go-worker`：任务执行、重试、下载与打包。
- `postgres`：业务真相源（任务、事件、配置、产物索引）。
- `redis streams`：异步调度与削峰，不承载业务真相。

### 2.2 边界原则

- API 层只做协议转换、鉴权与输入校验，不承载业务流程。
- 业务编排在 service 层，数据访问通过 repo 抽象。
- 下载与打包作为独立领域模块，避免和 HTTP/DB 耦合。

### 2.3 统一状态机

`QUEUED -> RUNNING -> SUCCESS | FAILED | CANCELED`

- 取消为显式命令流。
- 所有状态流转写入事件表，支持审计与排障。

---

## 3. 代码结构设计

```text
go-backend/
  cmd/api
  cmd/worker
  internal/
    app/           # 依赖装配
    http/          # handler/middleware/dto
    domain/        # 实体与状态机
    service/       # 用例与编排
    repo/          # postgres实现
    queue/         # redis streams实现
    downloader/    # 抓取/下载/打包
    config/        # 配置加载与校验
    obs/           # 日志/metrics/tracing
  migrations/
  tools/migration/

web/
  src/pages
  src/components
  src/api-client
  src/state
```

### 结构约束

- `domain` 不依赖 `repo/http/queue`。
- `service` 只依赖抽象接口。
- 前端只通过 `api-client` 访问后端，不在页面内直写协议字段。

---

## 4. 数据模型与全量迁移设计

### 4.1 核心数据表

- `tasks`：任务主记录与执行快照。
- `task_assets`：产物信息（路径、大小、校验和、可用性）。
- `task_events`：状态变迁与关键行为事件。
- `app_settings`：运行配置快照。

### 4.2 迁移流程

1. 切换窗口开始，冻结旧系统写入。
2. 导出旧系统任务/日志/配置数据。
3. 执行新 schema 初始化与批量导入。
4. 按批次校验：计数、状态分布、关键字段一致性。
5. 全量校验通过后切流新系统。

### 4.3 迁移保障

- 迁移工具支持断点续跑。
- 批次导入提供 checksum 与比对报告。
- 任一关键校验失败即中止切换。

## 5. API 与前端重构设计

### 5.1 API 策略

统一新版协议前缀：`/v2/*`

- `POST /v2/tasks`
- `GET /v2/tasks`
- `GET /v2/tasks/{id}`
- `POST /v2/tasks/{id}/cancel`
- `GET /v2/tasks/{id}/artifact`
- `GET /v2/dashboard/summary`
- `GET /v2/settings`
- `PUT /v2/settings`

### 5.2 前端策略

- 前端按新版协议重构，不保留旧协议兼容。
- 页面消费 view-model，由 `api-client` 统一映射后端结构。
- 错误与重试反馈统一交互组件管理。

---

## 6. 质量门禁与验收标准

### 6.1 工程门禁（必须全部通过）

- `go test ./...`
- `go test -race ./...`
- `go vet ./...`
- 前端构建与核心 E2E（创建任务/取消/下载/筛选）通过。
- 架构、迁移、回滚、运维文档齐全。

### 6.2 业务门禁（必须全部达标）

- 成功率不低于旧系统基线。
- 平均任务完成时长不高于旧系统。
- 关键接口 P95 达标。
- 数据迁移关键字段一致率 100%。

### 6.3 发布门禁

- 预发布环境完成一次完整迁移演练。
- 切换窗口内 smoke 清单全部通过。
- 任一红线失败即中止发布。

---

## 7. 风险与应对

- 风险：单阶段切换故障面大。
  - 应对：切换前完成全量迁移演练与压测，切换窗口内严格执行冻结与验收清单。
- 风险：协议重定导致前后端联调密集。
  - 应对：先冻结 OpenAPI/DTO，再并行开发；联调以契约测试驱动。
- 风险：历史数据质量差异。
  - 应对：迁移工具内置字段归一化与异常报告，保留失败记录重放入口。

---

## 8. 交付里程碑（5-8 周）

- 第 1-2 周：新架构骨架、协议冻结、迁移工具骨架。
- 第 3-4 周：核心业务与前端重构、全量测试补齐。
- 第 5-6 周：迁移演练、性能调优、发布手册定稿。
- 第 7-8 周：切换窗口执行、稳定性观察、遗留收尾。
