# 全栈重构与稳定性收敛设计（2026-03-16）

## 背景与目标

当前仓库已完成 Go 主线与前端源码收敛，但仍存在以下风险：

- 多层接口与兼容路径并存，维护成本偏高。
- 测试门禁虽完整，但缺少“先稳定后重构”的分阶段执行护栏。
- 前后端业务规则存在重复映射，问题定位链路较长。

本次设计目标：

1. 以“发布级验收”为第一优先级建立稳定基线。
2. 在稳定基线之上执行全栈重构（允许必要破坏性调整）。
3. 最终完成兼容层下线与全量验收，形成可持续演进单主线。

## 约束与范围

- 允许破坏性调整（接口、默认行为、配置结构可重整）。
- 必须提供迁移文档（旧→新映射、迁移命令、回滚要点）。
- 不接受“局部补丁式”修复；需要后端、前端、测试、部署脚本协同收敛。

## 分阶段方案（采用）

### S1：稳定性基线（发布级验收）

执行并拉通以下门禁：

1. `go test ./...`
2. `go test -race ./...`
3. `npm run test:frontend`
4. `npm run lint`
5. `npm run build`
6. `PYTHONPATH=. .venv/bin/pytest tests/web/test_go_proxy.py tests/web/test_routes_api_logs.py -q`
7. `npm run e2e:test`
8. `docker compose up -d --build` + `healthz/readyz` smoke + `docker compose down`

对失败项形成分级清单（P0/P1/P2）并优先清零 P0/P1。

### S2：全栈重构收敛

- 后端：入口层仅做协议转换，业务决策集中到应用层；状态机、下载/归档规则下沉为领域逻辑。
- 前端：页面入口与共享模块边界明确；轮询、错误映射、预检逻辑统一。
- 测试：按新契约重排单元/集成/E2E，清理失效与重复用例。
- 部署：更新 compose 与 runbook，明确切换与回滚路径。

### S3：兼容层下线与最终验收

- 删除临时兼容代码与重复接口。
- 全量门禁再次通过。
- 输出最终迁移文档与发布说明。

## 模块与数据流设计

### 后端分层

- **入口层**：`internal/httpui`、`internal/httpapi`、`internal/httpv2`
- **应用层**：统一任务编排服务（创建/复用/取消/状态推进/产物登记）
- **领域层**：状态机、错误分类、下载与元数据规则
- **基础设施层**：Postgres/Redis/文件系统适配器

### 前端分层

- 页面入口：`frontend/src/home`、`frontend/src/logs`、`frontend/src/settings`
- 共享模块：`frontend/src/shared/*`（polling、page_modules、archive_upload）
- 页面只表达渲染与交互意图，业务规则集中共享层。

### 核心数据流

1. 提交下载请求（含 metadata / force）。
2. API 做参数校验并交给应用层。
3. 应用层执行去重/复用/新建决策并落库。
4. Worker 消费队列推进状态机。
5. 产物生成后登记 artifact。
6. 前端轮询 summary + task list 展示状态。
7. 下载前通过 HEAD 预检，失败页内反馈。

## 错误处理与可观测性

- 统一错误模型：参数错误、业务冲突、依赖故障、内部异常。
- 统一错误码与前端提示映射，保留调试上下文。
- 关键链路日志包含 `task_id`、`stage`、`latency`、`error_class`。
- 取消操作、重试、pending reclaim 必须幂等。

## 测试策略

- 单元：状态机、决策逻辑、参数归一化、错误映射。
- 集成：API + queue + store 关键路径。
- E2E：提交任务、日志查看、下载预检、失败反馈、设置。
- 兼容：保留最小 Python bridge 回归直到兼容层下线。

## 完成定义（DoD）

- 发布级验收全绿。
- 无未关闭 P0/P1 问题。
- 破坏性变更具备迁移说明与可执行命令。
- 兼容层保留期限与下线点明确。
