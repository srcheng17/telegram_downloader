# 全仓收敛与性能/代码治理设计（方案 A）

## 1. 目标与约束

### 1.1 核心目标
- 以 `go-api + go-worker + postgres + redis + gateway` 作为唯一主运行链路。
- 在不明显改变用户可见行为的前提下，同时推进性能优化与代码收敛。
- 降低“双实现 + 双模板 + 双前端入口”带来的维护成本与回归风险。

### 1.2 明确约束
- 首页、日志页、设置页、下载接口与 Compose 入口保持基本兼容。
- 历史 Python 路径本轮不粗暴删除，先降级为兼容层与迁移参考。
- 优先解决高收益热点，不做界面重设计，不做大规模协议改名。

### 1.3 成功标准
- Go 成为唯一主实现，Python 不再承载新增运行时业务。
- 首页/日志轮询、任务查询与下载链路的资源消耗下降。
- 巨型文件拆分后职责边界清晰，新增需求不再继续堆到单文件。

---

## 2. 现状问题归纳

### 2.1 运行时事实来源不唯一
- Go 已是主线，但 Python/Flask 仍保留了一部分真实运行逻辑与兼容桥接。
- 相同概念在 `go-backend`、`telegram_downloader`、根目录 shim 中重复出现，边界不清。

### 2.2 UI 与前端存在重复维护
- 模板同时存在于根目录 `templates/` 与 `go-backend/internal/httpui/templates/`，已经出现内容漂移。
- `frontend/src/` 只是极薄入口，而真实业务逻辑仍集中在 `static/index.js`、`static/logs.js`。
- `static/dist/` 已有构建产物，但当前模板并未默认使用，说明构建链路与运行链路脱节。

### 2.3 核心文件继续膨胀
- `go-backend/internal/httpapi/api.go` 已承担过多职责：路由、参数解析、下载提交、日志、摘要、上传、错误响应。
- `static/index.js` 与 `static/logs.js` 既负责状态管理，又直接操作 DOM、轮询、上传控制与交互反馈。
- 这些文件继续演进会放大回归风险，并拖慢定位与测试效率。

### 2.4 性能热点较为集中
- 下载链路仍需要继续收敛 HTTP 复用、并发治理、进度写回与打包成本。
- 日志页存在定时轮询、全量 JSON 返回与频繁 DOM 更新的组合开销。
- 列表/摘要查询虽然已有基础索引，但仍存在进一步压缩请求成本与热路径逻辑的空间。

---

## 3. 目标架构

### 3.1 目标运行拓扑

```text
browser -> gateway -> go-api -> postgres/redis
                         |
                         +-> go-worker
```

- `go-api`：统一承接页面、legacy-facing API、v2 API、任务摘要与产物下载。
- `go-worker`：统一负责执行、下载、打包、状态推进、失败分类与进度写回。
- Python：仅保留兼容入口、迁移脚本、必要 shim 与兼容性测试。

### 3.2 代码事实来源收敛
- **后端事实来源**：`go-backend/`。
- **模板事实来源**：`go-backend/internal/httpui/templates/`。
- **前端源码事实来源**：`frontend/src/`。
- **静态产物目录**：`static/` 或 `static/dist/`，仅放构建输出与少量静态资源。
- **Python 事实来源**：`telegram_downloader/` 中仅保留 legacy/compat 范围，不再承接新业务。

### 3.3 分层目标
- `transport`：`httpui/httpapi/httpv2` 只做协议转换、校验、响应组装。
- `application/service`：任务提交、摘要聚合、下载提交流程、兼容桥接。
- `domain`：状态、错误、任务元数据、日志筛选规则。
- `infrastructure`：postgres repo、redis stream、downloader、artifact/open-file。

## 4. 优化策略

### 4.1 Go 主线可维护性优化
- 拆分 `cmd/server` 与 `cmd/worker` 的装配逻辑，降低入口函数复杂度。
- 以“查询/解析/响应/桥接”四类职责拆分 `httpapi/api.go`。
- 让 `legacy_adapter` 只保留协议兼容，不再承载核心业务判断。
- 继续拆解 downloader 内的页面解析、下载执行、护栏判断与打包逻辑。

### 4.2 前端收敛与性能优化
- 将首页、日志页、挂载器、共享状态模块化，逐步从 `static/*.js` 迁回 `frontend/src/`。
- 通过更细粒度的模块拆分，减少首页与日志页互相携带不必要逻辑。
- 优化轮询调度、无变化时的 DOM 更新与摘要刷新策略，降低前端执行开销。
- 让构建产物真正进入运行链路，消除“源码一套、产物一套、模板再一套”的漂移。

### 4.3 数据与查询路径优化
- 优先优化任务日志与摘要相关热路径，减少无效查询和重复聚合。
- 继续补齐最常见筛选/排序场景的索引与查询辅助封装。
- 对进度写回、轮询频率与下载回调做节流/去重，减少写放大和轮询放大。

### 4.4 Python legacy 收敛
- 根目录 `app.py`、`downloader_logic.py`、`task_store.py` 保持 shim 属性，不再扩展功能。
- `telegram_downloader/web/routes.py` 等文件明确标记 compatibility-only。
- 对仍有迁移价值的逻辑做边界标注；无法继续复用的部分冻结，不再双边实现。

---

## 5. 数据流与错误处理

### 5.1 统一数据流
- 用户入口保持不变：提交任务、查看日志、调整设置、下载产物。
- 运行时数据流统一为：`UI/API -> Go handlers -> repo/queue -> worker -> artifact`。
- legacy Python 仅做兼容代理，不再拥有独立业务真相。

### 5.2 错误模型
- 输入校验错误、可重试错误、永久失败、取消态、依赖故障分层处理。
- 用户可见文案尽量稳定，内部错误以结构化字段表达，避免散落字符串判定。
- 兼容层只负责翻译与映射错误，不再生成新的业务状态。

---

## 6. 测试与验收

### 6.1 测试策略
- Go 作为主测试面：`httpapi/httpui/httpv2/store/worker/downloader`。
- 前端重构重点依赖 `lint + build + Playwright`，必要时补少量无 DOM 依赖的轻量单测。
- Python 测试收缩为兼容哨兵，只验证 shim 与 legacy 行为未意外断裂。

### 6.2 验收要求
- 现有关键用户路径不回归：提交、重复任务确认、日志轮询、取消、artifact 下载、设置保存。
- Go 测试、竞态测试、前端构建、E2E 仍能作为主门禁。
- 代码结构能体现唯一事实来源，重复文件不再继续增长。

---

## 7. 分阶段落地

### Phase 1：高收益低风险治理
- 拆分 Go API 巨型文件中的纯逻辑与辅助模块。
- 把前端核心状态与轮询逻辑抽成模块，减少巨型 IIFE。
- 优化日志/摘要查询与轮询热路径。

### Phase 2：主线收敛
- 模板统一到 Go UI。
- 前端源码统一到 `frontend/src/`，构建产物接入运行路径。
- Python 明确冻结为 compatibility-only。

### Phase 3：历史负担清理
- 删除不再使用的重复模板、重复入口与过时文档。
- 收拢 CI、文档与 runbook，确保仓库主线叙事一致。

---

## 8. 设计结论

采用**方案 A：Go 主线收敛 + 前端/模板唯一事实来源 + Python 兼容层降权**。

该方案最符合当前仓库状态与用户约束：既能保住现有行为与部署入口，又能在可控范围内解决性能热点、重复实现和巨型文件继续恶化的问题。
